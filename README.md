# Enterprise Payment Migration Lab: Azure SQL → Databricks (Learning Project)

[简体中文](README.zh-CN.md) | **English**

**Status**: small local end-to-end demo + cloud implementation templates + **1.2 TB target-scale design**. Not a completed 1.2 TB migration or validated 21V deployment.

## Quick start (Python 3, standard library only)
```bash
python local/migration_lab.py demo --rows 10000
```
Demo initializes a synthetic payment source and target, runs a consistent snapshot, verifies, creates 4 change events (updates, delete, insert), applies incremental sync, verifies exact row equality, replays sync and verifies again. Local simulation uses SQLite on both sides; it does **not** test Spark, Azure SQL, CDC engine or Delta Lake.

For stepwise learning:
```bash
python local/migration_lab.py init --rows 10000
python local/migration_lab.py snapshot
python local/migration_lab.py verify
python local/migration_lab.py mutate
python local/migration_lab.py sync
python local/migration_lab.py verify
```

## Layout
- `local/migration_lab.py`: executable snapshot + change capture event log + replay + reconciliation demo (SQLite simulator)
- `databricks/01_full_load.py`: monthly payment-time JDBC batch load with month-scoped Delta replacement **template**
- `databricks/02_cdc_merge.sql`: latest-event Delta MERGE **template** with soft-delete markers; requires ordered CDC staging
- `databricks/03_reconciliation.sql`: source/target aggregate, monthly, merchant, and duplicate-key reconciliation SQL
- `sql/azure_sql_cdc_setup.sql`: Azure SQL CDC example, requires DBA permissions
- `docs/scale_plan.md`: 1.2 TB throughput planning, risk register and cutover gates
- `docs/governance.md`: metadata/security checklist
- `docs/technical_qa.md`: project overview and technical Q&A
- `docs/project_overview.md`: project structure, run/test instructions, and Mermaid flowcharts

## Testing

Run the standard-library unit tests and the local end-to-end smoke test:
```bash
python -m unittest discover -s tests -v
python local/migration_lab.py demo --rows 10000
```
The tests use temporary SQLite databases. The demo also uses SQLite only; it does not validate the Azure SQL or Databricks templates. **The `demo` command resets `data/source.db` and `data/target.db`**; see [docs/project_overview.md](docs/project_overview.md) for step-by-step commands and cloud validation boundaries.

## Important limitations and next engineering work
1. Local SQLite change-events are explicitly generated by the demo, *not* Azure SQL CDC or a general-purpose trigger.
2. SQLite snapshot is read under a transaction; the demo executes mutations afterward. Concurrent cutover correctness has not been demonstrated.
3. Databricks templates are not integrated with a deployed workspace; UC catalog/schema/tables, SQL Server JDBC driver, and the CDC landing process must be provisioned.
4. The monthly full-load template and CDC MERGE template are separate steps. MERGE assumes correctly staged, ordered changes; production processing still needs durable offsets and robust handling of late events.
5. The actual 21V network, Azure China service availability and identity approach must be validated in a real subscription.
6. Source 1.2 TB table sizes and time estimates are hypothetical; no performance result is asserted.
